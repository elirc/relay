# Sol: initial Relay design challenge

Relay's important failure window is after the mock provider records a notification but before the worker checkpoints that step. The provider therefore needs its own durable SQLite file and a unique idempotency key derived from the run and step, stable across worker attempts. Replaying the same key and intent must return the existing receipt. A different message under the same key should be rejected. Worker memory alone cannot prevent duplicate effects after a crash.

Worker leases and fencing guard the app database. A claim must atomically persist a new lease token and expiration; every step checkpoint and final status update must check that token and the current run state. A worker whose lease expired or was replaced must not advance the run. Lease fencing does not undo an already accepted external effect; the provider's idempotency contract supplies that separate guarantee. Long `wait` steps require renewals or a safe reclaim path.

Published workflow versions must be immutable snapshots. Runs pin one version and resume from persisted checkpoints, including the exact prior output, even when a draft is edited or a later version is published. Automatic retry state and next attempt time belong in SQLite, and canceled runs must not restart. Input, output, JSON body size, declarative step fields, and step count need explicit limits; no arbitrary code or network target should enter the workflow definition.

Acceptance includes a worker process deliberately exiting after provider acceptance and before checkpoint, a second worker resuming after lease expiry, and one provider receipt after completion. A separate stale-token test is needed because killing a worker alone does not prove fencing. I will test version pinning, idempotent run creation, cancellation, bounded retries, invalid definitions, and persistence across web/worker restarts. This is a durable local simulation, not a claim of exactly-once delivery to arbitrary services.
