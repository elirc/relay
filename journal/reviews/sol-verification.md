# Sol: independent Relay verification

I wrote `tests/adversarial.test.js` and `tests/durability.test.js` against the agreed API and exported store/worker primitives. Each process test uses fresh temporary app and provider SQLite files. The suite never touches the demo databases. The direct store test advances a synthetic clock: worker A claims a run, its lease expires, worker B reclaims with a different token, and A's attempted checkpoint returns false while B's succeeds. That establishes the fencing behavior independently of the crash test.

The real crash test starts the web server, creates a transform-plus-notify run, and launches a separate worker with `CRASH_AFTER_EFFECT_ONCE=1`. The worker exits with code 86 immediately after the provider accepts the notification. At that point the app database has one transform checkpoint and a still-running run, while the separate provider database has one receipt. A restarted worker reclaims the expired lease, completes the notify checkpoint, and finishes the run on attempt 2. The first checkpoint keeps its original row ID; the provider still has exactly one receipt. Web restart preserves the completed run and receipt. The mock provider honors a stable `runId:stepIndex` key. This demonstrates the cooperating mock boundary, not exactly-once delivery to arbitrary external systems.

The final full independent run passed **9/9** tests. Other checks verify actual execution against old and new published versions after a draft edit, immutable version metadata, run-key replay and conflicting intent, invalid/oversized declarative definitions, aged session denial, two competing workers claiming one run once, canceling an active wait before notify, two scheduled transient retries followed by terminal failure at attempt 3, manual recovery on attempt 4, and persistence of a 50,000-character inline output after restart. A larger Unicode output fails before checkpoint. Starting the web process and two workers concurrently against a fresh shared database also succeeded and processed a seeded workflow.

The separate provider database, worker leases, bounded retry state, and step checkpoints were observed through both API responses and process exits. The fault flag is test-only; no real network provider was involved. Cancellation stops later steps but cannot retract an already accepted provider receipt, as the product contract states.
