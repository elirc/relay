RELAY ARCHITECTURE CLINIC
========================

Read this alongside the fictional story walkthroughs and the actual source.
The architecture described as current exists in the rebuild. Proposed ports,
integrations and operational improvements are exercises, not delivered features.


1. NAME THE THREE DIFFERENT IDENTITIES
--------------------------------------

A run-request key identifies an operator's attempt to create one run. A lease
token identifies temporary permission for one worker claim. A provider key
identifies one externally accepted step effect. These are not interchangeable.

Example: run request K creates run 42. Worker A receives lease token L1.
Notify at step index 2 uses provider key "42:2". After a crash, worker B receives
L2 but uses the same provider key. Replaying K returns run 42, not another run.

If the provider key contained L1, recovery under L2 would look like a new
external effect. If the request key were reused as the key for every notify
step, different notifications in one run would collide. If the worker ID alone
were the lease token, a later claim by the same worker could be confused with
an earlier one. Identity should match the lifetime of the thing it protects.

This is a useful review technique in other systems: circle every ID and ask
what it identifies, who creates it, how long it lives, and what reuse means.


2. LOCATE THE AUTHORITATIVE STATE
---------------------------------

The app database owns workflow definitions, run lifecycle, claims, checkpoints,
retry schedule and events. The separate provider database owns accepted
notification receipts. Browser state owns an unsaved draft and the current
view, but does not establish that a step ran.

Source navigation:
  src/app.js: validation, draft/publish/run routes, retry/cancel and sessions.
  src/store.js: persistence, claims, lease checks, checkpoints and receipts.
  src/worker.js: step execution, heartbeat, recovery and transient faults.
  src/server.js: the web process and HTTP lifecycle.
  scripts/start.js: supervisor that starts and stops web plus worker.
  public/app.js: editor state, polling ownership and explicit draft recovery.
  tests/adversarial.test.js: API contracts and deterministic lease checks.
  tests/durability.test.js: real worker crashes, contention and persisted data.
  tests/lifecycle.test.js: supervisor and child process shutdown.
  tests/browser.mjs: editor, execution and recovery from the user's view.

The receipt adapter is invoked locally, not over a network. Its independent
transaction is enough to demonstrate the effect/checkpoint gap, but it does
not exercise DNS, packet loss, remote rate limits or real credential handling.
State the boundary before interpreting the test as evidence.


3. USE A FAILURE MATRIX INSTEAD OF A HAPPY-PATH DIAGRAM
------------------------------------------------------

Consider one notify step:

Failure point                 Durable evidence           Recovery idea
Before provider acceptance    prior checkpoints only      attempt the step
After acceptance, before      receipt, missing current    retry same provider
  app checkpoint                checkpoint                 key and checkpoint
After checkpoint, before      receipt and checkpoint      skip completed step;
  run completion                                           finish remaining work
After run success, before     succeeded run and key       return existing run
  HTTP status is observed

The second row is the hard one. From the app checkpoint alone it resembles
the first row, but repeating the effect has different consequences. Durable
provider deduplication resolves that ambiguity for the local adapter.

Now add a stale worker. Its external work may finish after its database lease
expires. The token check rejects its checkpoint, but cannot erase a provider
effect that already happened. The stable provider key and matching-payload
check address a separate failure boundary from the lease fence.

A stronger design description says exactly which component enforces each
claim. "Exactly once" without naming the effect, identity, retention and
cooperating component is too vague to guide either code or tests.


4. CHECKPOINT ORDER IS AN EXECUTION CONTRACT
--------------------------------------------

The current workflow is a linear list. checkpointStep checks the pinned
definition, current lease and step index. New checkpoints must be contiguous:
the count of completed steps must equal the next index. A repeated checkpoint
is accepted only when its serialized output matches the stored one.

This makes recovery straightforward. Load the saved outputs, take the final
one or the initial input, and continue from checkpoints.length. It depends on
the invariant that completed indices form a prefix, not an arbitrary set.

A future graph executor cannot reuse this assumption unchanged. Two independent
nodes may complete in either order; a count cannot identify which dependencies
are satisfied. The right next abstraction would be durable node identities
and transition rules, not simply a more complicated for-loop.

There is another current limit: a wait's deadline is created in memory when
the step begins. If the worker crashes before that wait is checkpointed, the
replacement repeats the full configured wait. Completed waits are skipped,
but partially elapsed wait time is not persisted. That behavior is observable
and should not be described as an exact durable wall-clock timer.

An extension for minimum-until-time waits would store a step deadline before
waiting, then resume only the remaining interval. It needs rules for clock
changes, cancellation and when the deadline is first established. Define
those semantics before calling either implementation a timer service.


5. LEASE DURATION IS A TRADEOFF, NOT A MAGIC CONSTANT
----------------------------------------------------

A short lease recovers abandoned work quickly but is easier to lose during
a pause. A long lease tolerates pauses but delays recovery after a crash.
The worker renews periodically and stops acting on a lost lease. Database
checkpoints independently verify ownership rather than trusting heartbeat
success from an earlier moment.

Synchronous JavaScript or database work can delay the event loop and therefore
heartbeats. Adding CPU-heavy arbitrary code to this worker would change the
timing assumptions. Moving such work to a separately controlled execution
environment would require its own limits, cancellation and result ownership.
The current bounded step language avoids promising an untrusted-code sandbox.

When checking a lease in a write transaction, sample time after lock acquisition.
Otherwise a delayed caller can use stale time to justify a write. The store's
optional explicit time inputs make deterministic tests possible; real callers
normally rely on its current-time behavior.

A multi-machine deployment would additionally need a clock policy and a
shared store suitable for that deployment. Shared-file local tests do not
demonstrate distributed clock behavior or cross-region availability.


6. A RETRY POLICY HAS SEVERAL INDEPENDENT LIMITS
-----------------------------------------------

The current code persists retry_count, next_attempt_at and total claim attempt.
It uses exponential backoff for recorded transient failures and permits manual
retry of a failed run while retaining checkpoints. A crash reclaim increments
attempt but does not necessarily record a new transient failure.

That distinction prevents a misleading statement: MAX_ATTEMPTS is a bound
on the configured failure retry policy, not a universal deadline after which
any repeatedly crashing run can never be claimed. A production design could
add maximum total attempts, maximum elapsed run age, a poison-run state and
operator quarantine. Those are future policies.

Jitter would reduce synchronized retry bursts. Provider concurrency limits
would prevent a recovered backlog from flooding one dependency. A retry
budget shared across many runs could protect a failing service. Each policy
has a different scope; a single per-run counter cannot do all those jobs.

Before adding retries, classify what retrying could change. A temporary
unavailability may clear. A permanently invalid payload will not become valid
because a timer elapsed. An uncertain accepted effect requires identity or
reconciliation, not merely waiting longer.


7. DURABLE DOES NOT MEAN UNBOUNDED
----------------------------------

Outputs are serialized and limited to 64,000 UTF-8 bytes. Workflow requests
have an aggregate 256 KB JSON limit; individual field limits do not override
it. JavaScript string length and serialized UTF-8 size are not identical.
Escapes, non-ASCII characters and JSON overhead matter.

Keeping output in the checkpoint transaction makes the persisted reference
simple: the data is there with the record. Moving output to object storage
can accommodate larger payloads but adds at least two crash windows: object
exists without a checkpoint, or a checkpoint references an object later lost
or removed. Integrity, retention, authorization and garbage collection become
part of execution correctness.

The current run and receipt list APIs also return bounded recent results.
An operator dashboard count and a paginated historical search would be a
separate feature. Do not infer that a record is absent merely because it is
not in a limited recent list.


8. OPERABILITY BEGINS WITH PROCESS OWNERSHIP
--------------------------------------------

npm start launches a supervisor, a web child and a worker child. A useful
shutdown must stop accepting work, let controlled cleanup occur, close stores
and disconnect IPC channels. An IPC connection can keep a process alive even
after its apparent application work is finished.

The delivered lifecycle test starts the actual supervisor, completes work,
requests shutdown and confirms exit plus a closed HTTP listener. A web-only
health test would miss an orphan worker or a supervisor kept alive by IPC.

For a production extension, distinguish liveness from readiness. A live
process can still have inaccessible storage; a working web app can have no
healthy workers. Queue age, lease reclaim count, repeated failures and effect
reconciliation backlog are often more useful than an HTTP 200 alone.

Backups must include a coherent understanding of both databases. Restoring
the app database without corresponding provider history can change what
retries mean. The local guidance is to stop processes before copying the full
data directory. A real deployment needs tested backup/restore procedures and
a policy for external effects that cannot be rolled back with local storage.


9. WHEN WOULD A BROKER OR SERVICE SPLIT HELP?
--------------------------------------------

A broker can distribute notifications of available work and absorb bursts.
It does not automatically replace durable run state or eliminate duplicate
delivery. If committing a run and publishing a queue message are separate,
an outbox or another explicit coordination policy is needed to prevent a
committed run from being forgotten or a phantom message from being executed.

A database-backed queue is reasonable here because the system is local and
small enough to inspect. Revisit it when measured polling or write contention,
deployment constraints, or operational needs justify the added boundary.
Keep tests for version pinning, request identity, lease ownership and effect
recovery when changing transport.

Likewise, a separate provider service would make network failures realistic,
but it would not change the logical need for a stable effect key. Separate
deployment is an implementation choice; the contract should remain explicit.

End an architecture review with a counterexample and a measurement, not a
list of fashionable components. "Under this crash history we can create a
duplicate receipt" is actionable. "We need more microservices" is not enough
to specify a correct next change.
